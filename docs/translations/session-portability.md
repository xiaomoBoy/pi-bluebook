# 会话为什么也要归你

> - **参考原文**　*The Session You Cannot Take With You*
> - **作者**　Earendil Engineering `<rfc@earendil.com>`
> - **发布于**　2026-07-30
> - **原文地址**　[earendil.com/posts/session-portability](https://earendil.com/posts/session-portability/)
> - **本文整理**　小墨／Pi 学习蓝皮书

我最初把 Agent 会话当成聊天记录。任务结束了，最终文件也生成了，这一页对话似乎就没用了。等到任务变长，我开始让 Pi 读文件、运行命令、修改项目，再把一部分工作交给其他 Agent，才意识到会话本身也是工作成果的一部分。

最终文件告诉我做出了什么。会话还能说明它为什么这样做，中间读过哪些材料，执行过哪些命令，哪里失败过，后来又怎样改了方向。

Earendil Engineering 在原文里提出了一个很尖锐的问题。你保存下来的聊天记录，究竟是一份能独立使用的工作记录，还是远程服务里某段状态的入口。这个问题改变了我看待 Pi 会话的方式。

## 一份会话里到底有什么

先拿蓝皮书自己的工作举例。假设我让 Pi 整理一份会议记录，它可能经历下面这些动作。

1. 读取 `input/项目会议记录.md`。
2. 找出负责人、截止时间和待确认事项。
3. 把行动清单写入 `output/action-items.md`。
4. 运行命令检查文件是否真的存在。
5. 根据检查结果再改一次。

聊天窗口只展示了这段过程的一部分。完整工作记录还包括工具调用、工具返回、当前工作目录、模型变化、分支和压缩摘要。Pi 会把会话自动保存成 JSONL 文件，按工作目录组织。你可以用 `/session` 查看当前会话的信息，也可以用 `/export` 导出供人阅读的文件。

这两个命令解决的是记录问题。它们不会自动把每一项远程状态都变成可携带的数据。原文讨论的托管搜索就是一个例子。服务商在远程完成 Web 搜索时，客户端可能只得到引用链接，看不到模型当时收到的完整排序、摘录和筛选过程。后来重新打开链接，也未必能还原当时的证据。

## 我现在怎样判断一份会话能不能带走

原文给出了五项测试，包括检查、导出、重放、审计和删除。我把它们换成自己做任务时会问的五个问题。

### 我能看见 Agent 当时看见的材料吗

文件内容、搜索结果和工具返回决定了模型怎样判断。记录里只有一句“已完成搜索”，人就没法复核当时依据了什么。

### 离开原来的服务后，这份记录还能读吗

本地文件、普通文本和清楚的路径容易保存。只剩响应 ID、远程文件 ID 或无法解读的数据块时，后续工作仍然依赖原服务。

### 换一个模型还能接着做吗

模型不会给出完全相同的下一句话。只要它能读懂目标、进度、关键决定和已有产物，接手工作就有了基础。

### 出问题后能查到原因吗

Agent 改错文件时，我需要知道它收到的任务、使用的工具和实际返回。只有最后一句“修改完成”，这次工作很难审计。

### 我知道数据还留在哪里吗

本地会话可以定位和删除。远程保存的对话、缓存或文件引用也要有清楚的保存规则。看不见保存位置，删除就只剩一个模糊的承诺。

这五个问题来自原文的可携带性框架。它们在这里被重新组织成普通 Pi 用户可以使用的检查动作。

## Pi 给我的一个重要习惯

我不再把所有关键信息只留在聊天里。长任务开始后，我通常会让项目目录里出现几份普通文件。

```text
project/
├── PLAN.md
├── DECISIONS.md
├── SOURCES.md
└── output/
```

`PLAN.md` 记录目标、步骤和验收条件。`DECISIONS.md` 留下已经确定的选择与原因。`SOURCES.md` 保存真正用过的资料和链接。最终产物继续放在 `output/`。

这些文件都能被人直接打开，也能交给另一个模型。会话仍然重要，但任务不再完全依赖会话记住每个细节。

## 跟着做一次最小检查

这次练习不会改动 Pi 设置。请在自己的练习目录里启动 Pi，然后完成下面的动作。

### 给会话起名

在 Pi 输入区输入下面的命令并按 Return。

```text
/name 蓝皮书会话检查
```

输入 `/session`。结果中能看到刚才的名称、会话文件、消息数量和用量信息，说明命名成功。

### 让关键决定落到文件

把下面这段任务交给 Pi。

```text
请在当前目录创建 DECISIONS.md，写下这次练习的目标、
已经完成的动作和下一步。完成后读取文件并核对三项是否齐全。
```

随后自己打开 `DECISIONS.md`。不要只看 Pi 的完成说明。

### 导出会话

回到 Pi 输入区运行下面的命令。

```text
/export session-check.html
```

退出 Pi 后，在当前目录确认 `session-check.html` 存在并能打开。导出的页面和 `DECISIONS.md` 是两种记录。前者保留过程，后者保留接手任务时最需要的信息。

## 这篇原文带给我的变化

以前我更关心模型能不能把任务做完。现在我还会看任务能不能复核，过几天能不能继续，换一个工具后还能不能读懂。

这也影响了我使用子 Agent 的方式。任务描述、权限范围和交付物最好保留成可读文字。子 Agent 给出结果后，主 Agent 还要能够解释它做了什么。工作规模越大，这份记录越重要。

会话可携带性听起来像服务商和开发者才需要研究的问题。落到普通用户手里，它对应一个很朴素的要求。做过的事情应该留得下来，留下来的东西应该看得懂。
