# 别让缓存命中率带偏任务

> - **参考原文**　*Prompt Caching In Agents*
> - **作者**　Earendil Engineering `<rfc@earendil.com>`
> - **发布于**　2026-07-22
> - **原文地址**　[earendil.com/posts/prompt-caching](https://earendil.com/posts/prompt-caching/)
> - **本文整理**　小墨／Pi 学习蓝皮书

我第一次留意 Pi 底部的 cache 数字时，很自然地把它理解成“缓存了答案”。这个理解会带来一串错误判断。缓存高，不代表模型记得更牢；缓存低，也不代表当前回答一定更差。

Earendil Engineering 的文章从 Agent 每轮怎样组织输入讲起。读完以后，我开始把 token、cache、cost 和任务结果分开看。四个指标彼此有关，承担的工作并不相同。

## Agent 每一轮都在重复发送大量内容

普通聊天已经会携带历史消息。Pi 还要加上系统说明、工具定义、项目规则、读过的文件、工具调用和执行结果。

假设第一轮输入是下面这段内容。

```text
[系统] [工具] [项目规则] [用户任务]
```

工具运行以后，下一轮会继续发送前面的内容，再在末尾加上新结果。

```text
[系统] [工具] [项目规则] [用户任务] [工具调用] [结果]
```

对话增长到几万 token 后，每次从头计算都会变慢，也会增加费用。提示缓存让提供商复用已经处理过的相同前缀，只计算新追加的部分。

它复用的是模型处理输入时产生的中间计算状态。网页缓存常常直接交回旧文件，提示缓存仍然会让模型生成新的回答。

## 为什么一个词的变化也可能有影响

提示缓存依赖相同的 token 前缀。两段文字在人眼里意思接近，分词结果或顺序不同，模型看到的输入就已经变了。

可以把它想成两条从开头逐项比较的序列。

```text
旧输入  A B C D E F G
新输入  A B C X E F G
              ↑
          从这里开始不同
```

前面的 `A B C` 仍有复用机会。从 `X` 开始，后面的计算需要重新进行。实际能否命中还取决于提供商怎样保存缓存、请求被路由到哪里，以及缓存是否已经过期。

模型切换通常会使用另一套模型状态。工具定义或顺序变化，会让靠前的输入改变。上下文压缩会用摘要替换早期消息，也会形成新的前缀。分支的情况更细一些。分支点之前仍然相同的前缀可能继续复用，分支后的新内容会重新计算。

## 缓存、上下文和项目记录要分开

这三个词经常被混在一起。

| 名称 | 它处理什么 | 用户最该关心什么 |
| --- | --- | --- |
| 上下文 | 模型当前这一轮能够看到的输入 | 关键信息有没有进入当前输入 |
| 提示缓存 | 相同输入前缀的重复计算 | 延迟和费用有没有减少 |
| 项目记录 | 写在文件里的目标、决定和产物 | 人和其他模型能否重新读取 |

缓存不能替代项目记录。缓存命中很高，模型仍可能因为早期要求写得含糊而走错。项目文件写得清楚，即使缓存失效，另一个模型也能重新读取并继续。

## 哪些正常操作会改变缓存

下面这些操作都有正当用途。

- 切换到更适合当前任务的模型。
- 加载、移除或更新工具和 Extension。
- 修改系统提示或项目规则。
- 从较早的节点创建新分支。
- 压缩过长的上下文。
- 请求被服务商路由到没有对应缓存的计算节点。

我不会为了保住缓存而拒绝这些操作。模型选错了，该换就换。上下文太长，该压缩就压缩。安全范围需要收紧，也应该先调整工具权限。

缓存是一项运行条件。任务质量仍然排在前面。

## 跟着观察一次缓存变化

不同模型提供商的计费和显示方式会变化，这个练习不要求你得到某个固定数字。我们只观察趋势。

### 确认当前显示

在 Pi 中输入 `/session`，看看当前会话的消息、token 和费用信息。Pi 的底部状态栏也会显示上下文、缓存和成本。

请把当前模型名称记下来。练习过程中不要切换模型，也不要修改工具。

### 在同一会话继续两轮

选择一个小文件，让 Pi 先概括内容，再让它根据刚才的概括列出三条需要核对的问题。两轮之间保持同一会话和同一模型。

观察第二轮的缓存信息。已有前缀可能得到复用，具体数字由当前提供商决定。

### 只记录，不追求命中率

把看到的结果写成下面这样。

```text
模型名称
第一轮输入量和缓存信息
第二轮输入量和缓存信息
是否切换模型或执行压缩
最终结果是否通过验收
```

如果第二轮没有出现预期的缓存，不要立刻修改配置。缓存可能过期，请求也可能被路由到别处。先确认任务结果，再查当前提供商的缓存规则和计费说明。

## 长任务里怎样少做无谓的改变

读完原文以后，我保留了几条很实际的习惯。

任务开始前先选好模型和需要的工具。项目规则放在稳定文件里，避免每一轮临时换一套说法。重要阶段完成以后再考虑压缩。准备尝试完全不同的方向时，可以开分支或新会话，别在原任务中反复改动前部上下文。

这些习惯能够减少无谓的重复计算，也让工作过程更清楚。它们不用于追求一个漂亮的 cache 百分比。

## 这篇原文帮我解开的一处误会

上下文变短，账单未必马上变低。一次压缩会生成摘要，也会改变输入前缀。很长的上下文如果保持稳定，提供商可能以较低的缓存读取价格处理其中一部分。具体结果仍要看当前模型、提供商和缓存保留规则。

因此，我不再凭输入长度猜费用，也不会只看缓存命中判断一次任务是否健康。我会一起看实际成本、响应速度和产物质量。最后一项仍然要靠验收。

提示缓存影响 Agent 执行长任务时的速度和费用。它没有替我们解决目标含糊、材料错误和验收缺失。把这些问题分清，状态栏里的数字才开始有用。
