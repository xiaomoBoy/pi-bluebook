# Agent 中的提示缓存

> **英文原题**：*Prompt Caching In Agents*  
> **作者**：Earendil Engineering `<rfc@earendil.com>`  
> **发布日期**：2026-07-22  
> **原文**：[earendil.com/posts/prompt-caching](https://earendil.com/posts/prompt-caching/)  
> **中文摘要与学习延伸**：小墨／Pi 学习蓝皮书

## Agent 为什么特别需要缓存

普通聊天和 Agent 对话都会带上历史消息。Agent 还会添加工具定义、项目说明、文件内容、工具调用和执行结果。连续工作时，新一轮输入的大部分前缀和上一轮完全相同。

提示缓存的核心作用，是让模型提供商复用这段已经处理过的前缀。它不是把模型的答案直接存起来，也不是传统的网页缓存。复用的是模型计算输入前缀时产生的中间状态。

## 为什么“前缀完全相同”很重要

缓存通常依赖精确的 token 前缀。只要前面的内容变化，从变化位置开始就无法继续使用原来的缓存。这种变化可能来自：

- 切换了模型。
- 增删了工具，工具的描述或顺序变了。
- 系统提示或项目上下文文件变了。
- 从早期消息创建了另一条分支。
- 执行压缩，用摘要替换了早期消息。

这并不意味着不能切换模型、不能分支或不能压缩。分支前仍然相同的前缀可能继续复用，实际命中还取决于提供商、路由和缓存保留。这些产品和工作流选择会影响缓存连续性，却不应被简化成“一分支就全部失效”。

## 缓存命中与成本

不同提供商对缓存写入、缓存读取和普通输入的计费不同，缓存也可能有有效时间。因此，“已命中多少缓存”只是理解成本的一部分。真正计算时，要同时查看提供商的当期计费规则与 Pi 显示的实际用量。

作者也用这个机制解释，为什么 Pi 不会为了减少当前 token 数，频繁修剪早期内容。一次简单删减会让从删除点开始的输入不再与原缓存前缀一致，后面的内容因此需要重新处理。

## 本站学习延伸

新手不需要围绕缓存去设计每一次对话。更重要的是三件事：

1. 看懂 Pi 底部显示的模型、上下文、缓存和成本是不同指标。
2. 知道切换模型、压缩和分支有实际用途，也会改变输入前缀。
3. 优化成本前先保证任务质量，不要用高缓存命中率替代结果验收。

这篇文章给我的一个重要提醒是：上下文更小不总是更便宜，一次删减也可能换来更多重复计算。

## 术语对照

| 英文 | 本站译法 | 简要理解 |
| --- | --- | --- |
| prompt caching | 提示缓存 | 复用已经处理过的输入前缀 |
| exact token prefix | 精确 token 前缀 | 从开头起完全一致的 token 序列 |
| cache read | 缓存读取 | 使用之前已计算的缓存状态 |
| cache write | 缓存写入 | 创建新的可复用缓存状态 |
