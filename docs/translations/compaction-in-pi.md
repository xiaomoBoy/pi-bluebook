# 压缩前先给下一棒留下交接

> - **参考原文**　*How Compaction Works in Pi*
> - **作者**　Earendil Engineering `<rfc@earendil.com>`
> - **发布于**　2026-08-13
> - **原文地址**　[earendil.com/posts/compaction-in-pi](https://earendil.com/posts/compaction-in-pi/)
> - **本文整理**　小墨／Pi 学习蓝皮书

长任务做到一半，Pi 仍然记得目标，却漏掉了早先提过的限制。很多人会把这种情况统称为“模型忘了”。我读完 Earendil Engineering 对 Pi 压缩机制的解释后，才把这里面的几件事分开。

模型每次回答都有一个有限的上下文窗口。系统提示、工具定义、项目说明、历史消息、工具调用和工具结果都会占用它。任务继续推进，输入越来越长。Pi 需要在达到上限前，把较早的内容收束成更短的表示，给后面的工作腾出位置。

这个过程叫 compaction。蓝皮书统一译为“上下文压缩”。

## 先把一次对话看成不断变长的输入

第一次发送任务时，模型收到的内容大致是这样。

```text
[系统说明] [工具] [项目规则] [用户任务]
```

Pi 调用工具后，下一次请求还会带上工具调用和返回结果。

```text
[系统说明] [工具] [项目规则] [用户任务]
[工具调用] [工具结果] [新的处理]
```

文件读得越多，命令输出越长，这段输入增长得越快。上下文达到模型上限后，请求会失败。Pi 因此会在接近阈值时自动压缩，也允许用户用 `/compact` 手动触发。

压缩以后，模型接到的内容更接近下面这样。

```text
[系统说明] [工具] [压缩摘要] [近期原始消息] [新任务]
```

早期记录仍留在会话文件里。下一次发给模型的上下文已经换了形态。理解这个区别很重要。会话保存回答“历史还在不在”，上下文压缩回答“模型下一轮会看到什么”。

## Pi 在压缩时保留什么

根据原文和 Pi 官方文档，Pi 会从最近的消息向前计算保留范围，把更早的一段交给模型生成结构化摘要。较近的消息继续以原始形式留在上下文中。摘要会记录目标、限制、完成进度、关键决定、下一步和重要文件。

Pi 默认还会累计追踪读过和改过的文件。单次工具返回太长时，序列化进摘要请求的内容可能被截断。摘要可以保留“读过这个文件”，却未必保存那次输出的每一行。

这就是我不把压缩理解成无损打包的原因。它更像一次工作交接。接班的人能知道项目做到哪里，也可能错过早先随口提到、当时没有写入产物的细节。

## 哪些内容最容易在交接里变淡

下面几类信息值得提前落盘。

- 只在对话中出现过一次的特殊限制。
- 很长的命令输出里某一行异常。
- 几个方案之间已经排除掉的选择。
- 用户临时纠正过的名称、语气或验收标准。
- 还没有写入文件的下一步安排。

这不是说 Pi 的摘要一定会漏掉它们。摘要本身由模型生成，输入又可能很长。重要信息只在聊天里出现一次，风险自然更高。

## 我现在怎样准备一次压缩

任务还在早期时，我让 Pi 自动处理就够了。任务跨过几个阶段以后，我会先留一个检查点。

```markdown
# 当前交接

## 目标
完成 Pi 学习蓝皮书的移动端排版修复。

## 已完成
- 首页和文章页已检查。
- 390px 宽度没有页面级横向滚动。

## 不能改变
- 保留浅米白方格背景。
- 全站继续使用自定义域名。

## 下一步
检查搜索层和移动菜单的背景色。
```

这份文件有一个明确作用。压缩摘要出了偏差，我仍然有一份自己能读、能够核对的当前状态。

## 跟着做一次压缩练习

这项练习适合放在一个已经聊过几轮、但没有重要生产操作的练习会话里。短到只有两三条消息的会话没有练习价值。

### 写出压缩后必须保留的内容

让 Pi 在当前目录创建 `CHECKPOINT.md`，至少写入任务目标、一项已经完成的工作、一项限制和下一步。

自己打开文件，确认四项都在。缺少任何一项就先补，不要急着压缩。

### 给压缩一个明确重点

在 Pi 输入区运行下面的命令并按 Return。

```text
/compact 请重点保留当前目标、用户限制、已修改文件、失败原因和下一步。
```

等待压缩完成并重新回到输入区。过程中不要反复提交 `/compact`。

### 检查交接是否还能继续工作

压缩完成后发送下面这段话。

```text
请根据当前上下文说明任务目标、已经完成的工作、不能改变的限制和下一步。
然后读取 CHECKPOINT.md，对比是否存在遗漏或冲突。暂时不要修改文件。
```

这里要验收两件事。Pi 能否复述四类关键信息，以及它能否用项目文件纠正摘要中的遗漏。只有回答“压缩成功”还不算完成。

## 压缩也会改变缓存

压缩前的输入以早期原始消息开头。压缩后的输入在相同位置换成了新摘要。从第一个变化的 token 开始，旧的提示缓存无法继续完整复用。后续请求会围绕新的前缀重新积累缓存。

这带来一个实际取舍。压缩能释放上下文空间，也会产生一次摘要成本，并改变原有缓存前缀。频繁手动压缩没有必要。上下文已经接近上限，或者任务准备进入新阶段时，它才真正有用。

## 这篇原文改变了我什么

我过去更容易把长会话看成一条不能中断的线。会话越长，越舍不得另开，也担心压缩以后前面的工作白做。

现在我把任务进度分成两层。会话负责保留完整过程，项目文件负责保存接手任务需要的事实。压缩只改变模型下一轮看到的上下文，它不会替我删除会话文件，也不该承担全部项目记忆。

真正可靠的长任务，应该允许模型在一次好的交接之后继续。这个思路后来也影响了我安排子 Agent。任务交出去以前先写清范围和产物，接回来以后再检查文件。上下文怎样变化，工作都还有落点。
