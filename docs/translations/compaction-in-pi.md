# Pi 的上下文压缩如何工作

> **英文原题**：*How Compaction Works in Pi*  
> **作者**：Earendil Engineering `<rfc@earendil.com>`  
> **发布日期**：2026-08-13  
> **原文**：[earendil.com/posts/compaction-in-pi](https://earendil.com/posts/compaction-in-pi/)  
> **中文摘要与学习延伸**：小墨／Pi 学习蓝皮书

## 长对话为什么不能一直原样保留

模型每一轮都需要接收当前上下文，而上下文窗口有容量上限。对话、工具调用和返回结果不断增长，最终会逼近这个上限。

Pi 的压缩不是删除整个会话文件。它会在模型将要继续工作时，保留较近的原始消息，并把更早的部分收束成一份摘要。后续轮次使用这份摘要衔接早期历史。

## 摘要保留的是工作线索

压缩的目标是让 Agent 能够继续任务。因此，摘要应当关注目标、已完成工作、重要决策、当前状态和下一步。它不会逐字保存所有交流，也难以保留每个微小但可能在后面变得重要的细节。

作者介绍了 Pi 自动压缩和手动 `/compact` 的角色。手动压缩还可以携带自定义要求，帮助摘要聚焦于接下来真正需要的信息。

## 压缩会改变后续输入

对模型来说，“早期原始对话”与“一份新生成的历史摘要”是不同的 token 序列。所以压缩不仅可能损失细节，也会打破原有提示缓存的连续前缀。后续轮次会从新的压缩状态开始积累缓存。

这也解释了为什么“只要上下文更小就一定更省”并不总是成立。你不应为了短期数字频繁压缩，而应把它当成长对话继续前的状态转换。

## 本站学习延伸

1. 任务目标和验收标准要写进项目文件。
2. 关键错误、决策与进度不要只留在对话里。
3. 执行 `/compact` 前，先检查下一阶段仍需要哪些信息。
4. 压缩后让 Pi 重读计划和当前产物，并复述接下来的一两步。

这样做能让任务不再依赖一次无损的对话记忆，压缩后仍有可核对的项目记录。
