## 很多人都问Pi Agent算什么，我就把它类比成游戏角色：

<span class="tweet-meta">2026-08-12 13:28:15 · 小墨原文</span>

> 很多人都问Pi Agent算什么，我就把它类比成游戏角色：
>
> Claude Code：满级程序员角色，装备和技能都配好了，直接进副本干活。
>
> Codex：工程型角色，更擅长接任务、改代码、跑测试、完成完整的软件工程流程。
>
> Hermes：长期跟着你的伙伴 NPC，会记住你、帮你跑定时任务、调用各种工具。
>
> 而 Pi Agent 更像是——角色编辑器。
>
> 模型、工具、Skill、Prompt、工作流都可以自己组合。
>
> 你不是在选择“这个 Agent 好不好用”，而是在决定：
>
> 我要把它做成什么样的 Agent。
>
> 所以我觉得 Pi 最有意思的地方，不是它开箱有多强，而是它把“造 Agent”这件事交给了你。

## 谁能想到，Pi Agent 的控制台除了写代码，居然还能拿来打游戏。

<span class="tweet-meta">2026-08-25 08:34:30 · 小墨原文</span>

> 谁能想到，Pi Agent 的控制台除了写代码，居然还能拿来打游戏。
>
> 给大家推荐 pi-extensions 里面一个好玩的项目：pi-arcade
>
> 不需要再打开另外一个游戏窗口，直接就能把小游戏显示在 Pi 的终端界面里。
>
> 等 Agent 跑测试、编译项目或者执行长任务的时候，就可以玩会小游戏摸会儿鱼。
>
> 它目前内置了 5 款游戏：
>
> 1. sPIce-invaders：Pi 版小蜜蜂，控制飞船打敌人，还有关卡和 Boss。
>
> 2. picman：Pi 版吃豆人，在迷宫里吃 Token，同时躲避各种 Bug。
>
> 3. ping：类似经典 Pong 的乒乓球游戏，你和 Pi 对打，先拿到 5 分获胜。
>
> 4. tetris：终端版俄罗斯方块，支持旋转、暂存、预览、分数和等级。
>
> 5. mario-not：实验性的马里奥风格横版闯关游戏，可以移动、跳跃、吃金币和挑战不同关卡。
>
> 正经的Pi插件玩多了，反倒是想找一些这样有意思的项目玩一玩，这也就是Pi 的魅力所在。
>
> 只要你想，你就可以，因为它是自由开放的，你甚至可以拿它玩游戏，是不是有我的世界那个味道了😂

>
> 玩法其实很简单。

>
> 等 Context 快到 100% 的时候，只能疯狂按：/compact
> 把周围的 Token 压缩掉，再继续苟一会。
>
> 甚至还做了 Cache Hit，捡到之后可以暂时降低 Context 增长速度，说实话，这游戏设定基本就是我最近研究 Pi 的精神状态，完全是写实的。

> 但是最有意思的部分是，这个游戏我一行代码都没动，是完全没写。
>
> 我只是把上面的想法丢给了 Gear Zero，跟它说我要一个 Pi Agent 在 Context Window 里面躲 Token 的生存游戏，然后它自己规划、写代码、做画面、搭玩法，最后直接在浏览器里跑出来了。

> 如果是我以前遇到这种事情，我的第一反应肯定是：
> 先让 AI 写代码，再开项目，再调一堆东西，最后花半天时间修 Bug。
>
> 现在反过来了，我只负责描述这个游戏到底应该怎么玩。
> 剩下的交给 Agent。
>
> 当然，现在“跟 AI 聊天做游戏”本身已经不算特别新鲜了，我这次真正觉得 Gear Zero 有点意思的反而是后面，第一版出来不满意，可以继续跟它聊。Token 太少了，就让它加，/compact 不够爽，就继续改。

> 游戏太简单，就继续加机制。
>

>
> 因为以前 AI 做游戏，更像是：

## Pi 为什么一直不做桌面端？

<span class="tweet-meta">2026-08-27 09:51:08 · 小墨原文</span>

> Pi 为什么一直不做桌面端？
>
> 我最近研究下来发现，可能不是没做，而是它根本没打算自己做，把功能开放给第三方。
>
> 一开始我是抱着好奇的态度去寻找答案，Pi 都发展这么久了，终端体验已经很完整，但官方一直没有 Desktop App，也没有移动端的适配。
>
> 后面仔细看了一圈，我才慢慢理解它背后的思路。
>
> 1、Pi 官方做的其实不是“客户端”
>
> Pi 更核心的东西一直是 Agent Runtime、Session、Tool、Extension 这些底层能力。我们平时看到的终端，只是其中一种交互方式，而不是 Pi 唯一的产品形态。
>
> 2、官方其实早就把接口留好了
>
> 除了终端模式，Pi 还有 SDK、JSON、RPC，可以让第三方直接控制 Session、发送 Prompt、接收 Tool Call 和 Streaming 事件。
>
> 所以理论上你完全可以做成桌面 App、Web、手机端，甚至直接集成进 IDE，底下跑的还是同一个 Pi。
>
> 3、这样反而不用重新造一套 Agent
>
> 第三方只需要解决 UI 和交互，不需要重新实现模型调用、Session、Tool、Extension 这些东西。
>
> 这也是为什么现在社区已经慢慢出现 Desktop、Web 控制台、手机遥控等不同实现。
>
> 4、Pi 可能根本不想规定 Agent 应该长什么样
>
> 看到这里我才理解，Pi 不做官方桌面端，可能并不是少了一个功能，而是它从一开始就把 Agent 和客户端分开了。
>
> Pi 核心思想：只负责把底座做好，至于其他怎么使用，或者想要什么样的功能，都是交给社区自己去创造。

</article>

## 今天看到，JetBrains 给 Pi 做了一个 GUI 客户端🔥

<span class="tweet-meta">2026-08-27 11:40:51 · 小墨原文</span>

> 今天看到，JetBrains 给 Pi 做了一个 GUI 客户端🔥
>
> 从我的角度来说还是命令行最舒服，但是GUI、TUI才是大众更能接受的表现形式。
>
> 如果想把Pi 分享给更多的人，GUI这条路总要有人来跑一跑。
>
> JetBrains 给 Pi 做的 GUI 客户端，叫做ThinkRail，底层的引擎还是 Pi，比如模型、skills、压缩还是交给Pi自己管，但是外面多了一层能看的工作区。
>
> 这次的GUI 我觉得比较有意思的点有三个：
>
> 1.、聊天、编辑器、终端摊在一个界面里
> 不用来回切窗口，改哪看哪，Agent 在干什么一眼能跟上。
>
> 2. 一个仓库能开多个工作区
> 每个 Agent 单独一条 git worktree，界面上并排跑，main 不会被一起改乱。这才是多 Agent 能看懂的 GUI，不是多开几个对话框。
>
> 3. 规格和改动都能看见
> Spec graph + diff 在界面上，中间态不会只剩最终结果。想回溯，不用翻一堆日志。
>
> 虽然命令行的形式符合 Pi 这条极简路线，但是在复杂的工作当中，如果有人帮我配置和安装好对应的功能，我想大家也会很高兴，最主要的是终于有一条能把人留住的 GUI 路径。
>
> 使用什么是你的权利，但是社区给你提供不一样的选择，这和Pi的理念不谋而合

</article>

## 最近研究 Pi 的时候，我发现社区其实已经做出了不少桌面端和移动端项目🔥

<span class="tweet-meta">2026-08-27 16:12:20 · 小墨原文</span>

> 最近研究 Pi 的时候，我发现社区其实已经做出了不少桌面端和移动端项目🔥
>
> Pi 官方一直没有自己做 Desktop App，但是 SDK、RPC、Session 这些底层能力都已经开放了，所以很多第三方项目其实只是给 Pi 换了一个更舒服的入口。
>
> 我挑几个比较值得玩的：
>
> Pi Desktop：目前比较完整的 Pi 桌面端，直接复用原来的 Session、模型登录和 Extension，终端里的 Pi 基本可以无缝搬到 GUI。
>
> Pi Web：浏览器版 Pi 工作台，Session、文件、模型、Skill 都可以直接管理，目前 GitHub 已经 3K+ Star，社区热度很高。
>
> Remote Pi：我比较推荐的移动端方案，iOS、Android 都有原生 App，通过 Extension + 二维码就可以在手机上远程控制自己的 Pi。
>
> pi-mobile：更轻量的手机 Web 方案，不用安装 App，浏览器就可以接管 Session，还支持 Tailscale、Cloudflare Tunnel 和 Face ID / Touch ID。
>
> PI WEB：更偏多设备协同，Pi 可以一直跑在服务器或者工作站，浏览器关掉 Agent 也不会停，后面换手机、电脑、平板都可以继续接手。
>
> 用了这么多，我最中意的还是： PI WEB
>
> 主要还是默认设置的UI和风格真的让我很喜欢，简单就能实现多端设备的切换和兼容，因为本质上只是一个WEB应用，没有那么多复杂的配置。
>
> 社区把东西都弄好了，至于你想要终端、桌面还是网页，完全可以由你自己决定。

</article>

## 原来 MiniMax Code 2.0，也是基于 Pi 重做的。

<span class="tweet-meta">2026-09-08 00:43:42 · 小墨原文</span>

> 原来 MiniMax Code 2.0，也是基于 Pi 重做的。
>
> 说实话，我知道这个消息的时候很兴奋，越来越多开发者喜欢使用Pi Agent作为自己Agent产品的基座。
>
> MiniMax 官方自己也说：
>
> Rebuilt on the open-source Pi Agent framework。
>
> 我简单分析了一下他们之间的共性
>
> 共性：
>
> 1、底层都是 Coding Agent 这套逻辑
>
> 读文件、改代码、跑命令、调用工具，再围绕 Session 持续工作。
>
> 2、都开始很重视 Session 和长任务
>
> MiniMax Code 2.0 重做以后，也明显加强了任务连续性、状态保存和长任务稳定性。
>
> 3、都把扩展能力留出来
>
> Skill、工具、外部能力都可以继续往上叠。
> 但真正的差异更明显。
>
> MiniMax Code 2.0：尽量帮你把产品做好
>
> 它在 Pi 这套底座上继续加了桌面 UI、Browser Control、Remote Control、Goal、Memory、Plugin Marketplace、Office 能力等等。
>
> 虽然MiniMax Code 2.0被改造的没有了，Pi那个味道，但是从它是一个产品级的角度出发，是没有任何问题的，我更关注的是他基于Pi有没有做自己的创新。
>
> 如果在他之上有特别的创新，那就是成功。
>
> Pi 的意义更像是在提供一套 Agent 底座，人人都可以构建自己的Agent，给了大众可以自定义的机会。这也是我觉得Pi这个项目存在最大的意义。

## Pi V2 来了，可能要进入 Agent Runtime新时代🔥

<span class="tweet-meta">2026-09-08 10:14:33 · 小墨原文</span>

> Pi V2 来了，可能要进入 Agent Runtime新时代🔥
>
> 最近一直在关心 Pi 新的 Harness V2 版本的设计，我感觉新版本真正需要关心的事情，不再是单纯的功能增加而是整体方向的变化。
>
> 从简单的Coding Agent转向到了Agent Runtime，这才是我感觉这次变化最值得关注的。
>
> Coding Agent 很好理解，像 Pi Agent、Claude Code、Codex，你给它一个任务，它调模型、用工具、写代码，把这件事干完。
>
> 有点像一个你随叫随到的程序员。
>
> Agent Runtime 则更像给这个程序员准备了一间长期存在的办公室。人可以下班，电脑可以重启，甚至第二天换个人继续干，但任务、资料、进度都还在那里。
>
> 两者其实有很多共同点：
>
> 1、都要模型
> 2、都要 Tools
> 3、都需要 Context
> 4、都有 Agent Loop
>
> 其实一句话总结就是：
>
> Coding Agent：重点是把这一次任务做完。
>
> Agent Runtime：重点是让任务和状态长期存在。
>
> Pi V2 我现在最想看的，已经不是它 Coding 能力又强了多少，或者是功能增加了多少。
>
> 这些和我日常生活越来越远了，我更期待带Pi能在保持自己简洁的基础上，怎么慢慢变成一个让 Agent 长期活下去的 Runtime。
