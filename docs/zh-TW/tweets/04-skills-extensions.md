>
> 技能 目錄：~/.pi/agent/skills/ 和專案裡的 .pi/skills/gh /
> git CLI：提 PR、看 diff，比再套一層 GitHub MCP 乾淨
>
> ponytail：先複用現有程式碼，少生成一堆新檔案 commit-
>
> helper / pr-helper：提交和 PR 走 技能 + gh pi-context-view：每加一樣東西先看它吃多少 上下文 pi-agent-

## 推薦幾個新手使用Pi Agent 必裝的安全外掛程式！

<span class="tweet-meta">2026-08-24 11:29:39 · 小墨原文</span>

> 推薦幾個新手使用Pi Agent 必裝的安全外掛程式！
>
> 因為Pi Agent 預設幾乎沒有沙箱，也沒有完整的權限判斷。
>
> 但是不要覺得是 bug，其實是設計。Pi 預設就四個工具，read、write、edit、bash，權限跟你當前使用者一樣。模型一旦要刪檔案、改 `.env`、跑 `sudo`，它真能幹。對老手這叫乾淨，對新手這叫危險。
>
> 所以我一般會讓剛入門的人先裝幾樣防護，別一上來就裸奔。
>
> 1. safe-coder
> 一站式入門包。危險命令會先問你，`.env`、`.git`、`node_modules` 可以先阻擋一下。小白先裝這個最省事。
>
> 2. pi-permission-gate
> 官方示例同款思路。`rm -rf`、`sudo`、亂改保護路徑，先彈確認再執行。沒有介面時預設直接攔。
>
> 3. pi-protected-paths
> 專門護金鑰和敏感檔案。`.env`、憑證、常見配置，讀寫都會被擋住，避免模型手滑把金鑰吐出來或改壞。
>
> 4. pi-sandbox
> 更接近真正的沙箱。檔案和網路能按白名單控，工作階段裡還能開關。比單純彈窗確認更徹底，但也要多配一點。
>
> 5. pi-permission-modes
> 像權限擋位。預設確認、接受編輯、更自動，都能切換；特別危險的命令會直接封死。適合想一邊用一邊調鬆緊的人。
>
> 我非常建議小白的安裝順序：先 safe-coder，再加 pi-protected-paths。真要隔離環境，再上 pi-sandbox。
>
> Pi 其實本身已經很乾淨了，但是乾淨不等於安全。
>
> 先把護欄裝上，再去玩 技能 和外掛程式，安全才是第一位。

</article>

## 分享一下Pi 遠端裝置的方案，官方外掛程式+UU遠端，基本上就夠了

<span class="tweet-meta">2026-08-24 15:56:13 · 小墨原文</span>

> 分享一下Pi 遠端裝置的方案，官方外掛程式+UU遠端，基本上就夠了
>
> 外掛程式就推薦這五個：
>
> 1. 官方 SSH 擴充功能
> 本地跑 Pi，遠端操作 VPS 上的檔案、Shell、Docker。最接近“我還在本機，但手伸到伺服器”。
>
> 2. pi-mobile
> 手機或瀏覽器直接接管 Pi 工作階段（Session），能看 Tool Call、切模型、繼續對話。適合人不在電腦前，又想盯著任務往下走。
>
> 3. PI WEB
> Pi 常駐伺服器，多裝置用瀏覽器進同一個控制面。更接近完整遠端工作臺，而不只是臨時連一下。
>
> 4. remote-pi
> 社群外掛程式，主打手機遠端控制，後面還在往多 Pi、Agent Mesh 方向走。有點實驗性，但方向值得盯。
>
> 5. tmux + Tailscale + Pi
> 最樸素的一套。Pi 跑在伺服器，Mac 或手機隨時 SSH 回去，接著同一個 工作階段 幹。不依賴花活，穩。
>
> 我基本上是官方 SSH 擴充功能+pi-mobile 以前是Tailscale內網穿透的方式，但是還是很麻煩而且官方的節點也不一定穩定，現在直接使用官方外掛程式和VPS伺服器就能完成。
>
> 實在解決不了的問題，可以上UU遠端解決，基本上這一套組合拳下來，能滿足百分之99的人的遠端需求了！

</article>

## Pi 外掛程式和核心功能的邊界到底在哪裡？

<span class="tweet-meta">2026-08-26 23:10:34 · 小墨原文</span>

> Pi 外掛程式和核心功能的邊界到底在哪裡？
>
> 最近我一直在思考一個問題：什麼能力應該放進 Core，什麼能力應該永遠留給 擴充功能？
>
> 我覺得這是我研究Pi這麼久以來，最有意思的地方。
>
> Pi 一直堅持核心足夠輕，需要什麼能力就自己往上加，但隨著生態越來越大，子代理、Sandbox、Memory、Plan Mode、Remote 工作階段 這些東西也開始變得越來越常見。
>
> 很多時候大家都在討論的是“要不要加功能”，這個問題，我反倒覺得更應該弄清楚這三大邊界：
>
> 1、Agent 跑起來必須有的能力，應該進 Core
>
> 比如 工作階段、上下文、Tool Call、壓縮（Compaction），這些本身就是 Agent 正常工作的基礎。
>
> 2、決定安全和生態規則的能力，Core 至少應該提供標準
>
> 比如權限、遠端 工作階段、子代理 通訊，如果每個 擴充功能 都重新設計一套，最後反而會越來越亂。
>
> 3、具體怎麼玩，繼續留給 擴充功能
>
> Memory 用哪套、Plan Mode 怎麼設計、子代理 怎麼分工、搜尋工具用哪個，這些我反而希望 Pi 永遠不要替使用者決定。
>
> 我看了很多官方的材料和開源專案的說明，上面都把極簡貫徹到底，而且很多地方官方都說了，不會把不必要的功能加到核心裡面。
>
> 有一句話，我記得很深，能用外掛程式解決的絕不去動核心，我感覺這才是 Pi 最難守住，也是最值得我們這些開發值得期待的地方。

## Pi 套件 可能是最被大家忽然的功能🔥

<span class="tweet-meta">2026-08-28 13:41:31 · 小墨原文</span>

> Pi 套件 可能是最被大家忽然的功能🔥
>
> 很多人可能只知道Skill，但是沒仔細的去了解Pi Package這個功能，它解決的不是單個技能分享的問題，而是把你的使用習慣、配置、使用方式一起打包的實現。
>
> 他可以讓你把你的Pi Agent，完整的分享給你想要的人！
>
> 1、以前加能力是散的
>
> 這邊放一份說明，那邊改一處設定，用久了自己都說不清這套環境到底疊了什麼。套件 是把它們收成一份，裝上就能看見清單，這套東西突然變得清楚了。
>
> 2、它更像給某個場景備的工具箱
>
> 不是去市場裡收藏「必裝」。做研究就備搜尋和記憶，管機器就備遠端和日誌。一份包對應一種用法，換場景就換清單，主環境不會越堆越重。
>
> 3、能加上去，也能拿下來
>
> 這點其實很關鍵。今天試一塊，不合適明天拿掉，不會把整個 Pi 改成不敢動的狀態。能復原，才敢真的往上疊。
>
> 4、所以手感是從清單裡出來的
>
> 模型大家都能接。真正開始好用，是你為哪些事打過包、留下了哪些習慣。清單一短，用起來才像自己的工作方式，而不只是預設的 Coding Agent。
>
> Pi的功能是真的研究不完，總能在社群和官方找到一些有趣的實現，其實以前我也想過怎麼把自己的Agent分享出去，沒想到官方已經內建了。

> 玩到最後，我開始讓Pi自己改造自己🔥
>
> 最近我開始換一種方式使用 我的Pi。
>
> 以前 Agent 缺一個功能，我第一反應基本都是去找外掛程式、翻 GitHub，看看有沒有別人已經做好的。
>
> 但是現在不一樣了，很多時候我找的都不一定符合我的心意，所以慢慢的我開始自己讓它寫自己的外掛程式了。
>
> Pi本身就很輕，所以總結就是一句話：你缺什麼，就自己給自己補什麼。
>
> 我先拿一個很簡單的安全需求做測試。
>
> 平時 Agent 自己操作終端機，我還是希望一些高風險操作必須經過我確認，所以我直接把需求告訴 Pi，讓它自己研究應該怎麼實現。
>
> 最後整個過程比我想像中簡單很多：
>
> 1、我只負責說需求：哪些操作風險比較高，需要先經過我的確認。
>
> 2、Pi 自己想辦法實現：它會去理解自己的擴充機制，判斷這個能力應該放在哪一層。

> 3、做完以後再自己測試：不合適就繼續改，直到變成我真正願意長期留下來的功能。
>
> 這個思路我覺得比“推薦幾個 Pi 外掛程式”有意思多了。
>
> 因為每個人真正需要的功能其實都不一樣。
>
> 別人做好的外掛程式，解決的是別人的問題；讓 Pi 根據自己的使用習慣去寫，最後留下來的才更像自己的工具。
>
> 我猜肯定也會有人說，這是在重複造輪子，但是我更想說的是，這不就是你用Pi 給你自由度的意義嘛
>
> 世界上沒有兩片一模一樣的雪花，動手自己玩一玩吧，我想你也會覺得有趣的

## Pi 你必須學會的事，學會寫好AGENT.md🔥

<span class="tweet-meta">2026-09-02 13:57:15 · 小墨原文</span>

> Pi 你必須學會的事，學會寫好AGENT.md🔥
>
> 很多人在建立專案的時候，根本就沒有在意過或者根本就沒有AGENTS.md檔案，覺得這只是一個提示詞文件。
>
> 這有可能就是你的Pi 為什麼不按照你的指令去工作，編輯的規則轉頭就忘，每次都需要重新去提醒。AGENTS.md不只是一份簡單的文件，而是整個專案最高級別的準則。
>
> 社群裡已經出現過兩批人了，要不就更本不寫，要不就寫的太滿，什麼規則都往裡面塞，導致還沒開始用，Pi上下文就塞滿了東西。
>
> 我總結了以下三點：
>
> 1、全域性只保留習慣
>
> 根目錄的AGENT.md是對所有專案生效。這裡適合放你的個人習慣。比如說提交資訊的方式，不需要過於囉嗦，不確定的資訊和操作優先詢問。
>
