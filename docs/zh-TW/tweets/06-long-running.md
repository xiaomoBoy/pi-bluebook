# 把 Pi 變成長期工作流

**這一階段要解決的問題**　處理 VPS、遠端裝置、Runtime、介面與生態，讓 Pi 從一次任務走向長期使用。

最後一階段收錄長期執行、遠端存取、桌面端和生態專案。它們不都是必裝項，作用是幫助讀者判斷自己的 Pi 最後要執行在哪裡、服務什麼工作。

## 很多人都問Pi Agent算什麼，我就把它類比成遊戲角色：

<span class="tweet-meta">2026-08-12 13:28:15 · 小墨原文</span>

> 很多人都問Pi Agent算什麼，我就把它類比成遊戲角色：
>
> Claude Code：滿級程式設計師角色，裝備和技能都配好了，直接進副本幹活。
>
> Codex：工程型角色，更擅長接任務、改程式碼、跑測試、完成完整的軟體工程流程。
>
> Hermes：長期跟著你的夥伴 NPC，會記住你、幫你跑定時任務、呼叫各種工具。
>
> 而 Pi Agent 更像是——角色編輯器。
>
> 模型、工具、技能（Skill）、Prompt、工作流都可以自己組合。
>
> 你不是在選擇“這個 Agent 好不好用”，而是在決定：
>
> 我要把它做成什麼樣的 Agent。
>
> 所以我覺得 Pi 最有意思的地方，不是它開箱有多強，而是它把“造 Agent”這件事交給了你。

## 誰能想到，Pi Agent 的控制台除了寫程式碼，居然還能拿來打遊戲。

<span class="tweet-meta">2026-08-25 08:34:30 · 小墨原文</span>

> 誰能想到，Pi Agent 的控制台除了寫程式碼，居然還能拿來打遊戲。
>
> 給大家推薦 pi-extensions 裡面一個好玩的專案：pi-arcade
>
> 不需要再開啟另外一個遊戲視窗，直接就能把小遊戲顯示在 Pi 的終端機介面裡。
>
> 等 Agent 跑測試、編譯專案或者執行長任務的時候，就可以玩會小遊戲摸會兒魚。
>
> 它目前內建了 5 款遊戲：
>
> 1. sPIce-invaders：Pi 版小蜜蜂，控制飛船打敵人，還有關卡和 Boss。
>
> 2. picman：Pi 版吃豆人，在迷宮裡吃 Token，同時躲避各種 Bug。
>
> 3. ping：類似經典 Pong 的乒乓球遊戲，你和 Pi 對打，先拿到 5 分獲勝。
>
> 4. tetris：終端機版俄羅斯方塊，支援旋轉、暫存、預覽、分數和等級。
>
> 5. mario-not：實驗性的馬里奧風格橫版闖關遊戲，可以移動、跳躍、吃金幣和挑戰不同關卡。
>
> 正經的Pi外掛程式玩多了，反倒是想找一些這樣有意思的專案玩一玩，這也就是Pi 的魅力所在。
>
> 只要你想，你就可以，因為它是自由開放的，你甚至可以拿它玩遊戲，是不是有我的世界那個味道了😂

## Pi 為什麼一直不做桌面端？

<span class="tweet-meta">2026-08-27 09:51:08 · 小墨原文</span>

> Pi 為什麼一直不做桌面端？
>
> 我最近研究下來發現，可能不是沒做，而是它根本沒打算自己做，把功能開放給第三方。
>
> 一開始我是抱著好奇的態度去尋找答案，Pi 都發展這麼久了，終端機體驗已經很完整，但官方一直沒有 Desktop App，也沒有移動端的適配。
>
> 後面仔細看了一圈，我才慢慢理解它背後的思路。
>
> 1、Pi 官方做的其實不是“客戶端”
>
> Pi 更核心的東西一直是 Agent Runtime、工作階段（Session）、Tool、擴充功能（Extension） 這些底層能力。我們平時看到的終端機，只是其中一種互動方式，而不是 Pi 唯一的產品形態。
>
> 2、官方其實早就把介面留好了
>
> 除了終端機模式，Pi 還有 SDK、JSON、RPC，可以讓第三方直接控制 工作階段、傳送 Prompt、接收 Tool Call 和 Streaming 事件。
>
> 所以理論上你完全可以做成桌面 App、Web、手機端，甚至直接整合進 IDE，底下跑的還是同一個 Pi。
>
> 3、這樣反而不用重新造一套 Agent
>
> 第三方只需要解決 UI 和互動，不需要重新實現模型呼叫、工作階段、Tool、擴充功能 這些東西。
>
> 這也是為什麼現在社群已經慢慢出現 Desktop、Web 控制台、手機遙控等不同實現。
>
> 4、Pi 可能根本不想規定 Agent 應該長什麼樣
>
> 看到這裡我才理解，Pi 不做官方桌面端，可能並不是少了一個功能，而是它從一開始就把 Agent 和客戶端分開了。
>
> Pi 核心思想：只負責把底座做好，至於其他怎麼使用，或者想要什麼樣的功能，都是交給社群自己去創造。

</article>

## 今天看到，JetBrains 給 Pi 做了一個 GUI 客戶端🔥

<span class="tweet-meta">2026-08-27 11:40:51 · 小墨原文</span>

> 今天看到，JetBrains 給 Pi 做了一個 GUI 客戶端🔥
>
> 從我的角度來說還是命令列最舒服，但是GUI、TUI才是大眾更能接受的表現形式。
>
> 如果想把Pi 分享給更多的人，GUI這條路總要有人來跑一跑。
>
> JetBrains 給 Pi 做的 GUI 客戶端，叫做ThinkRail，底層的引擎還是 Pi，比如模型、技能、壓縮還是交給Pi自己管，但是外面多了一層能看的工作區。
>
> 這次的GUI 我覺得比較有意思的點有三個：
>
> 1.、聊天、編輯器、終端機攤在一個介面裡
> 不用來回切視窗，改哪看哪，Agent 在幹什麼一眼能跟上。
>
> 2. 一個倉庫能開多個工作區
> 每個 Agent 單獨一條 git worktree，介面上並排跑，main 不會被一起改亂。這才是多代理 能看懂的 GUI，不是多開幾個對話方塊。
>
> 3. 規格和改動都能看見
> Spec graph + diff 在介面上，中間態不會只剩最終結果。想回溯，不用翻一堆日誌。
>
> 雖然命令列的形式符合 Pi 這條極簡路線，但是在複雜的工作當中，如果有人幫我配置和安裝好對應的功能，我想大家也會很高興，最主要的是終於有一條能把人留住的 GUI 路徑。
>
> 使用什麼是你的權利，但是社群給你提供不一樣的選擇，這和Pi的理念不謀而合

## 最近研究 Pi 的時候，我發現社群其實已經做出了不少桌面端和移動端專案🔥

<span class="tweet-meta">2026-08-27 16:12:20 · 小墨原文</span>

> 最近研究 Pi 的時候，我發現社群其實已經做出了不少桌面端和移動端專案🔥
>
> Pi 官方一直沒有自己做 Desktop App，但是 SDK、RPC、工作階段 這些底層能力都已經開放了，所以很多第三方專案其實只是給 Pi 換了一個更舒服的入口。
>
> 我挑幾個比較值得玩的：
>
> Pi Desktop：目前比較完整的 Pi 桌面端，直接複用原來的 工作階段、模型登入和 擴充功能，終端機裡的 Pi 基本可以無縫搬到 GUI。
>
> Pi Web：瀏覽器版 Pi 工作臺，工作階段、檔案、模型、技能 都可以直接管理，目前 GitHub 已經 3K+ Star，社群熱度很高。
>
> Remote Pi：我比較推薦的移動端方案，iOS、Android 都有原生 App，通過 擴充功能 + 二維碼就可以在手機上遠端控制自己的 Pi。
>
> pi-mobile：更輕量的手機 Web 方案，不用安裝 App，瀏覽器就可以接管 工作階段，還支援 Tailscale、Cloudflare Tunnel 和 Face ID / Touch ID。
>
> PI WEB：更偏多裝置協同，Pi 可以一直跑在伺服器或者工作站，瀏覽器關掉 Agent 也不會停，後面換手機、電腦、平板都可以繼續接手。
>
> 用了這麼多，我最中意的還是： PI WEB
>
> 主要還是預設設定的UI和風格真的讓我很喜歡，簡單就能實現多端裝置的切換和相容，因為本質上只是一個WEB應用，沒有那麼多複雜的配置。
>
> 社群把東西都弄好了，至於你想要終端機、桌面還是網頁，完全可以由你自己決定。

## 研究Pi發現，長期穩定使用比什麼都重要🔥

<span class="tweet-meta">2026-08-28 15:40:33 · 小墨原文</span>

> 研究Pi發現，長期穩定使用比什麼都重要🔥
>
> 所以我覺得它更適合放在一臺VPS 上，而不是家裡的電腦。
>
> 以前我是裝在家裡電腦上面24小時跑，但是如果遇到斷電、系統自己休眠，體驗感會很差，工作直接被打斷了，讓我感到很煩躁，現在放在VPS問題都解決了
>
> 我自己用下來，比較明顯的就這幾點。
>
> 1、伺服器不會自我休眠
> 家裡電腦總會遇到斷電、更新、休眠。VPS 是一直線上的，任務可以掛著，回來還能接上，不用重新解釋一遍上下文。
>
> 2、24小時隨時待命
> 以前得坐在那臺機器前面。現在用手機、遠端連上去就能看它在幹什麼、接著下指令。控制權不綁在家裡那張桌子上。
>
> 3、家裡的電腦終於可以休息了
> Agent 佔著本機的時候，關機、休眠、拿去幹別的都會打架。放到伺服器上，互不影響，兩邊都輕快一點。
>
> 4、環境隔離，隨便折騰
> 本機今天裝東西、明天改系統，Agent 的配置很容易跟著漂。伺服器上相對乾淨，清單和習慣能留下來，用久了才像自己的那一套。
>
> 5、很適合長期任務
> 查資料、盯日誌、掛著處理零碎任務，這類事情最怕中途掉線。24 小時線上以後，Pi 才更像一個可以託付的助手，而不只是開機才存在的工具。
>
> 可能會有人問，不好做資料同步，其實很簡單使用Github就好了，我自己的內容和資料都放在了Github私有倉庫，如果有隱私資料就不建議了。
>
> 但是我這個方案不適合所有人，只適合需要長時間使用Agent的使用者，喜歡對你有幫助

## 我居然不知道，Pi 在遊戲方面也有貢獻🔥

<span class="tweet-meta">2026-08-29 12:56:17 · 小墨原文</span>

> 我居然不知道，Pi 在遊戲方面也有貢獻🔥
>
> Unity遊戲引擎，我想大家應該都有所瞭解，社群已經慢慢的開始，往這方面做遊戲處理。
>
> 最近我看到一個挺有意思的專案 pi-unity，它解決的不在是單純製作遊戲的問題，而是開始把Pi真正的帶入到遊戲開發相關的工作當中。
>
> 以前用 Coding Agent 做 Unity，流程基本都是 AI 改程式碼，我切回 Unity 等編譯，發現報錯，再把報錯扔回來，很多時候人其實是在兩個軟體中間來回搬運資訊。
>
> pi-unity 開始嘗試把這條鏈路接起來。
>
> 1、Pi 開始知道 Unity 此刻在發生什麼
>
> 它可以檢查當前開啟的是哪個專案、Unity 程序是不是存在、Pipeline 有沒有連上、專案現在能不能正常執行任務。
>
> 這個變化看起來不大，但意義不一樣。
>
> 以前 Agent 面對的是一堆 .cs 檔案，它只能通過程式碼去“猜”遊戲現在是什麼狀態；現在它開始能夠獲取 Editor 本身的狀態，知道自己到底在操作什麼環境。
>
> 2、寫完程式碼之後，它開始可以自己驗證結果
>
> 比如讓 Pi 修改一個角色系統，以前改完基本就結束了。
>
> 現在它可以繼續觸發 Unity 編譯，發現 Compiler Error 再回來修改，然後跑 EditMode / PlayMode Test，測試失敗繼續讀取結果處理。
>
> 也就是說流程慢慢變成了：
>
> 我告訴它想做什麼，剩下的編譯、測試、報錯、再修改，可以讓 Agent 自己來回跑。
>
> 3、最有意思的還是它開始進入正在執行的 Unity Editor
>
> pi-unity 可以通過 Pipeline 的 Roslyn REPL，在 Unity Editor 主執行緒執行受控的 C#。
>
> 比如讀取當前專案裡的某個設定、檢查執行狀態，甚至針對正在除錯的內容做一些臨時測試和調整。
>
> 它裡面甚至單獨做了一個 unity-interactive-playmode-authoring 技能，目標就是讓 Agent 在 Play Mode 裡面先檢查和除錯，再決定哪些東西真正需要持久化下來。
>
> 4、所以 pi-unity 真正讓我感興趣的，不是“Pi 也可以寫 Unity 了”
>
> 而是 Agent 正在從操作程式碼，慢慢往操作專業軟體發展。
>
> 今天是 Unity，後面也可能是 Blender、Unreal、CAD、影片剪輯軟體。
>
> 當這些軟體裡面的狀態、按鈕、執行環境都逐漸變成 Agent 可以理解和呼叫的 Tool，Vibe Coding 可能也不會一直停留在“幫我生成一個網頁”，而是真正的可以在遊戲生產當中製作出來。我自己想要的遊戲。

## 原來 MiniMax Code 2.0，也是基於 Pi 重做的。

<span class="tweet-meta">2026-09-08 00:43:42 · 小墨原文</span>

> 原來 MiniMax Code 2.0，也是基於 Pi 重做的。
>
> 說實話，我知道這個訊息的時候很興奮，越來越多開發者喜歡使用Pi Agent作為自己Agent產品的基座。
>
> MiniMax 官方自己也說：
>
> Rebuilt on the open-source Pi Agent framework。
>
> 我簡單分析了一下他們之間的共性
>
> 共性：
>
> 1、底層都是 Coding Agent 這套邏輯
>
> 讀檔案、改程式碼、跑命令、呼叫工具，再圍繞 工作階段 持續工作。
>
> 2、都開始很重視 工作階段 和長任務
>
> MiniMax Code 2.0 重做以後，也明顯加強了任務連續性、狀態儲存和長任務穩定性。
>
> 3、都把擴充能力留出來
>
> 技能、工具、外部能力都可以繼續往上疊。
> 但真正的差異更明顯。
>
> MiniMax Code 2.0：儘量幫你把產品做好
>
> 它在 Pi 這套底座上繼續加了桌面 UI、Browser Control、Remote Control、Goal、Memory、Plugin Marketplace、Office 能力等等。
>
> 雖然MiniMax Code 2.0被改造的沒有了，Pi那個味道，但是從它是一個產品級的角度出發，是沒有任何問題的，我更關注的是他基於Pi有沒有做自己的創新。
>
> 如果在他之上有特別的創新，那就是成功。
>
> Pi 的意義更像是在提供一套 Agent 底座，人人都可以構建自己的Agent，給了大眾可以自定義的機會。這也是我覺得Pi這個專案存在最大的意義。

## Pi V2 來了，可能要進入 Agent Runtime新時代🔥

<span class="tweet-meta">2026-09-08 10:14:33 · 小墨原文</span>

> Pi V2 來了，可能要進入 Agent Runtime新時代🔥
>
> 最近一直在關心 Pi 新的 代理框架（Agent Harness） V2 版本的設計，我感覺新版本真正需要關心的事情，不再是單純的功能增加而是整體方向的變化。
>
> 從簡單的Coding Agent轉向到了Agent Runtime，這才是我感覺這次變化最值得關注的。
>
> Coding Agent 很好理解，像 Pi Agent、Claude Code、Codex，你給它一個任務，它調模型、用工具、寫程式碼，把這件事幹完。
>
> 有點像一個你隨叫隨到的程式設計師。
>
> Agent Runtime 則更像給這個程式設計師準備了一間長期存在的辦公室。人可以下班，電腦可以重啟，甚至第二天換個人繼續幹，但任務、資料、進度都還在那裡。
>
> 兩者其實有很多共同點：
>
> 1、都要模型
> 2、都要 Tools
> 3、都需要 上下文
> 4、都有 Agent Loop
>
> 其實一句話總結就是：
>
> Coding Agent：重點是把這一次任務做完。
>
> Agent Runtime：重點是讓任務和狀態長期存在。
>
> Pi V2 我現在最想看的，已經不是它 Coding 能力又強了多少，或者是功能增加了多少。
>
> 這些和我日常生活越來越遠了，我更期待帶Pi能在保持自己簡潔的基礎上，怎麼慢慢變成一個讓 Agent 長期活下去的 Runtime。
